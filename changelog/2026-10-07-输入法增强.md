### 小布输入法：四码自动上屏的字被换成码表首选词

- 引擎自己在 native 里按四码上屏它词库里的字时，模块在提交出口按当前编码回查码表，提交的不是码表首选词就换成首选词
- 提交那一刻引擎可能已经把自己的编码清掉了，因此按键入口额外记一份「这一键按下去之后的编码」给提交出口兜底
- 提交对应的编码取「引擎当前编码 / 本次按键拼出的编码」里更长的那个 —— 引擎提交时经常已经把编码退回到上一个字母
- 用户点了模块注入的候选之后 800ms 内到达的提交不再被这一条接管

### 小布输入法：提交接管不再用上一段编码的首选词

- 引擎提交的编码比 pending 记的那个更长时，不再用 pending 换词，宁可上屏引擎自己的词

### 小布输入法：自定义方案下取消「四码上屏」

- 设置页里的「四码上屏」开关在自定义方案生效时置灰、置为关，并标注「自定义方案不支持」（与编码提示一致）
- 模块不再补四码唯一时上屏；为阻止引擎四码自动上屏写的按键拦截、提交吞掉、编码塞回等兼容代码一并删除
- 只保留五码顶屏：打满码表最长码后再按一键时上屏首选词

### 小布输入法：上屏后清掉残留候选帧

- 接管提交、以及模块自己上屏（四码唯一这类上屏后引擎编码就结束的情况）之后 200ms 内，引擎按残留编码推回来的候选帧直接清空，用户接着打字就立刻放弃清空
- 五码顶屏不设这个窗口：触发键已经交回引擎，紧接着推来的是下一段输入的正常候选

### 小布输入法：点已选中的自定义方案条目不再重播选中动画

- 点击处理先比对当前方案：已经是选中项就什么都不做，与原生方案条目的行为一致
- 原因：原来无条件 `refreshEntries()` 会整块重建条目（删掉再加回 + `setChecked`），radio 的选中动画因此多播一次

### 小布输入法：内置方案与自定义方案合成一块 panel

- 注入的条目与内置方案同组（`key_wubi_scheme` 分组），排在原生条目之后
- 顺手清掉此前版本可能残留在偏好树里的「自定义方案」独立分组（`key_custom_wubi_panel`）

### 小布输入法：修「点已选中的自定义方案会把 radio 取消选中」

  再后台写；**读不到时返回 `null` 就保持现状**，不瞎猜（猜「开」会在"用户刚关掉 + 写入失败"
  时把开关弹回开，看起来像开关不听话）。

### ⚠️ root 路径踩坑（重要）

- **`ProcessBuilder("su", ...)` 在应用进程里起不来**：应用进程的环境变量是 zygote 那套，
  `PATH` 里没有 `/system/bin`，直接 `IOException: Cannot run program "su": error=2`。
  改成按 `/system/bin/su` → `/system/xbin/su` → `/sbin/su` → `su` **逐个试绝对路径**。
- **KernelSU 对未授权应用会把 `su` 从 mount namespace 里隐藏**，表现同样是 `ENOENT`（`error=2`），
  容易被误读成"设备没 root"。`ModuleConsole.suUnavailableReason()` 把这种情形翻成
  「请在 KernelSU / Magisk 里给「输入法增强」授权 root」，与 `EACCES`（授权被拒）分开说。
- 因此这个开关**需要 root 授权**（写的是各输入法 `filesDir` 下的 `config.properties`，
  模块进程没权限直接进）。首次点开关若提示拿不到 root，去 KernelSU/Magisk 给模块授权即可。

## 2026-10-10 剪贴板开关改走 ContentProvider —— **不再需要 root**

### 起因

之前那个开关靠 `su` 把值写进各输入法私有目录（模块进程进不去别人的 `filesDir`），
于是这个纯本地开关被 root 绑住：要处理 PATH 里没有 `su`、KernelSU 把未授权应用的 `su`
藏起来（ENOENT，看着像"设备没 root"）等一堆设备侧问题。

但**真正需要的只是把「用户改了开关」这件事传达给注入侧**，方法不止 root 一种。

### 现在的数据流

```
模块界面 --同进程直接调--> ModuleSettingsProvider.write()（SharedPreferences 落盘）
                                    ↑ query（只读，白名单键）
        注入侧 ModuleConfig.sync() --+
                                    ↓ 写回本地
        /data/data/<输入法>/files/custom_wubi_.../config.properties
                                    ↓ 照旧读本地（热路径一行没改）
        ModuleConfig.clipboardUnlimited()
```

- 新增 `ModuleSettingsProvider`（`authorities=com.lookie.opluswubi.settings`，`exported=true`）：
  **对外只读**，只暴露 `clipboard_unlimited` / `support_simple_word` / `baidu_fix_wb_scheme` 三个键。
- 新增 `ModuleConfig.sync(context)`：按 `SYNC_INTERVAL_MS = 2000` **节流**，把 provider 的值抄回本地
  `config.properties`；拿不到 provider 就沿用本地旧值，什么都不做。
  `simpleWord` / `baiduFixEnabled` / `clipboardUnlimited` 三个读方法开头都调它。
- `ModuleConsole`：`clipboardUnlimited` 改成 `ContentResolver.query`；
  `setClipboardUnlimited` 改成 `ModuleSettingsProvider.write`（同进程，不走 Binder）。
  删掉 `storageDir()` / `CONFIG_FILE` 那套拼路径 + root 写文件的逻辑。

### ⚠️ 真机踩坑：provider 的写入鉴权不可靠

第一版想用 `Binder.getCallingUid() == applicationInfo.uid` 来"只放行模块自己"写，
结果 **`adb shell content update` 竟然真的写进去了**（日志里没有"拒绝外部应用"那条）——
说明这个判据在 CLI / 框架代理调用时不可靠。于是改成：

- `insert` / `update` / `delete` **一律返回 0 / null**（外部应用一个字都写不进来）；
- 写入只提供 `ModuleSettingsProvider.write(context, key, value)` 这个**进程内**方法；
- 模块界面与 provider 本来就在同一个进程，直接调即可，根本不需要跨进程写。

### 验证

- `content query` 能读到值；
- `content update`（shell 身份）被拒；
- 界面点开关 → provider 立刻变值（`false` → 再点回 `true`）；
- 注入侧真机日志：`已从模块同步配置：[clipboard_unlimited]`（百度进程，**没走 root**）。
- `BUILD_ID` → `2026-10-10-1410`。

## 2026-10-10（续）：修好百度剪贴板面板标题的上限数字

用户反馈：**百度显示 `2101/300`，逻辑生效了但文字没改**。

### 根因

标题里的 `300` 是 **`ClipboardPanelListView.h(List)` 里的硬编码字面量**，
既不读偏好表也不调 `ClipboardConfig.c()` —— 所以改裁剪逻辑 + 改偏好表都动不了它。

字节码证据（`classes3.dex`，资源 `string/clipboard_with_count` = `"剪贴板(%d/%d)"`，id `0x7f1203cb`，
全 dex 只有这一处引用）：

```
0x5d  invoke-interface List->size() -> I
0x6b  const v3, #0x03cb7f12                ; 0x7f1203cb
0x6e  invoke-virtual Resources->getString(I) -> String
0x76  const/16 v3, #300                    ; ★ 硬编码上限
0x78  invoke-static Integer->valueOf(I)
0x84  invoke-static String->format(String, Object[]) -> String
0x88  iget-object v7, this, ClipboardPanelListView.d   ; ★ 标题 TextView 字段名 d
0x8a  invoke-virtual TextView->setText(CharSequence)
```

### 改法

新增第三个 Hook：`ClipboardPanelListView.h(List)`。`proceed()` 之后把已设好的标题重写一遍
（`剪贴板(N/300)` → `剪贴板(N/100000)`），取「最后一段连续数字」当上限替换，
对资源文案改版不敏感；文本已是目标值就直接返回（`h()` 在热路径上，要零成本）。

> 反证记录：`Global.Y0` 一度被误判为上限，其实由 `DefaultCandSizeStrategy.e(I)` 写入，是**候选栏尺寸**。
> 早先挂的三层「通用文本改写」（`String.format` / `TextView.setText` / `ImeTextView.setText`）
> 一次都没命中的原因也在这里 —— 没找到真正写标题的那一句。

### 验证

- 真机日志：`已 Hook com.baidu.input.ime.front.ClipboardPanelListView.h(List)（把标题里的上限顶成 100000）`
- `BUILD_ID` → `2026-10-10-1430`

### 2026-10-10 追加：标题数字的**真正**落笔处（前两版都改错了）

前两版按资源反查（`string/clipboard_with_count`，全 dex 唯一引用点 = `ClipboardPanelListView.h()`）
去改，真机**毫无反应** —— `h()` 一次都没被调用。

改用「反向抓凶手」：临时 Hook `TextView.setText`，过滤「文本含 `/` 且调用栈含 `clipboard`」，
一次命中：

```
[嗅探] 面板写文本："0/300"    ← ClipboardSubTabView.<init>
[嗅探] 面板写文本："2101/300" ← ClipboardSubTabView.setCount
```

`com.baidu.input.clipboard.panel.view.ClipboardSubTabView.setCount(int)` 两条分支
把 `/300` 写死成**字符串字面量**（连 `String.format` 都没走）：
`const-string '</font>/300'`（超限红字分支）/ `const-string '/300'`（普通分支）。

**最终改法**：Hook `setCount(int)`，`proceed()` 后把条数 TextView（字段 `b`，`ImeTextView`）
上「最后一段数字」换成 100000。三处齐活：`ClipboardConfig.c()` + 偏好表 + `setCount`。

**教训**：「资源 id 唯一引用点」≠「真机走的那条路」—— 同一 dex 里硬键盘/触屏两套面板并存。

### 2026-10-10 追加：开关改完不生效 —— 换成「推送」通道（搜狗 / 小布都中招）

用户报：**「搜狗和小布连续修改不生效」**。

#### 现场证据（PLK110）

| 位置 | `clipboard_unlimited` |
|---|---|
| 模块 provider（真值源，用户在模块界面点开关写这里） | `false` |
| 小布私有目录 `config.properties`（注入侧热路径读的） | `true` |
| 搜狗私有目录 `config.properties` | `true` |

三处对不上 —— 用户在模块界面把开关**关掉**了，两家输入法却一直读到**开**。

#### 两个叠加的根因

**① 同步是「被功能带着走」的懒同步。**
`ModuleConfig.sync()` 只在**读配置的那一刻**顺带执行，而读配置的调用点全在功能热路径上
（小布是「插一条剪贴板记录」时、搜狗是「候选重排」时）。用户改完开关若没有再触发那条路径，
本地文件就一直停在旧值 —— 看着就是「改了不生效」。

**② `ContentProvider` 被 Android 11+ 的包可见性挡住。**
真机日志：

```
E ActivityThread: Failed to find provider info for com.lookie.opluswubi.settings
配置同步[轮询]：provider={clipboard_unlimited=null, ...} 本地={clipboard_unlimited=true}
```

调用方（输入法）manifest 里没有 `<queries><provider android:authorities="com.lookie.opluswubi.settings"/></queries>`，
`query()` 直接返回 null。**注意报的是「找不到 provider」而不是「权限拒绝」——特别像"模块没装"，
极具误导性。** 而目标输入法的 manifest 我们改不了。

实测规律：模块界面刚装完 / 刚打开（provider 进程热着）时 query 能成，**冷启动一律 null**。
所以这个 bug 时有时无，最难查。

#### 改法

新增 `ModuleSettingsBus`：模块界面一改开关，立刻
`sendBroadcast(Intent(ACTION).setPackage(输入法包名).putExtra(...))` ——
**广播用 `setPackage()` 显式指定包名，不受包可见性限制**（这是关键）。
注入侧在拿到宿主 Context 时注册一个**运行时 receiver**（`RECEIVER_EXPORTED`，
因为发送方是另一个应用；标 `NOT_EXPORTED` 会静默收不到，这个坑不报错，很隐蔽），
收到直接 `ModuleConfig.applyPushed()` 落盘。

于是变成**推 + 拉双通道**：

- **推送（主）**：即时、不受可见性限制，改完 1 秒内生效；
- **provider 轮询（兜底）**：每 5 秒拉一次，覆盖「推送时输入法进程没起」的情况；
- 同步启动点从「功能热路径」搬到 **`ImeEnv.bindContext()`**（拿到宿主 Context 就起，
  幂等），不再依赖任何功能被用到。

#### 顺带修掉的留痕问题

`ModuleConfig.syncNow()` 的日志改成**无条件打**（成功 / 无变化 / 全查不到都打），
把 provider 值、本地值、待更新项全打出来：

```
配置同步[轮询]：provider={clipboard_unlimited=false, ...} 本地={clipboard_unlimited=true} 待更新={clipboard_unlimited=false}
已从模块同步配置：[clipboard_unlimited]
```

老毛病是「只在成功时打」——失败路径一个字都不留，看起来像函数没被调用（2026-10-10 白跑一轮）。

#### 验证（真机自证）

```

收到配置推送：clipboard_unlimited=false

配置同步[节流到期]：本地={clipboard_unlimited=true} 待更新={}
```
